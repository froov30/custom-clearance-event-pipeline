# PRD: Customs Clearance Event Pipeline

> **Synthetic data.** Every event in this project is generated by a simulator. The reference
> formats are real (ISO 6346 container IDs, UN/LOCODE ports, 6-digit HS codes), but the data
> is not real-world data.

## 1. Problem

A shipment's customs clearance status is split across declaration, port and broker systems.
Their updates arrive **late, duplicated, out of order or malformed**. As a result, operations
teams find out that a container is stuck on an inspection hold only after it has already cost
them demurrage (port storage fees). Nobody has one reliable, current view of each shipment.

## 2. Users

| User | Need |
|---|---|
| **Ops analyst** | Wants to see which shipments are on hold, for how long, and get an alert before the cost builds up. |
| **Customs broker** | Wants a single shipment's current state and its full event history, including anything that looks wrong. |
| **Platform engineer** | Wants to run, scale and debug the pipeline: bad input must be quarantined (not lost), processing must be safe to replay, and health must be visible. |

## 3. Goals and non-goals

**Goals**
- G1: Give one correct, current state per shipment, even when its events arrive late, duplicated or out of order.
- G2: Never lose an event silently. Valid events are stored, and invalid ones are quarantined with a reason.
- G3: Alert on shipments that stay on hold longer than a threshold, once per hold.
- G4: Prove all of the above with a reproducible, one-command demo built on synthetic data.

**Non-goals**
- Integrating with real customs, port or broker systems
- A custom web UI (Swagger, a CLI and Kafka UI are enough)
- Multi-broker Kafka, a MongoDB replica set, or cloud deployment in the core scope (see the add-ons in IMPLEMENTATION_PLAN.md)
- Correcting clock skew between sources
- API authentication

## 4. User flows

1. **Ingest.** A source system (here, the simulator) publishes a clearance event. The pipeline validates it. A valid event is stored once; an invalid event goes to the dead-letter queue (DLQ) with a reason code.
2. **Check a shipment.** A broker calls `GET /shipments/{id}` and sees the state, how long it has been in that state, and any anomalies. They then call `/shipments/{id}/events` to see the history in event-time order.
3. **Triage holds.** An analyst calls `GET /shipments?state=ON_HOLD` and `GET /alerts` to find the shipments that are held too long.
4. **Investigate bad input.** An engineer calls `GET /rejections/summary` for DLQ counts by reason, and reads the raw messages in Kafka UI.
5. **Demo and verify.** An engineer runs the demo command. It reports produced, stored, duplicate, rejected, state, anomaly and alert counts, and checks them against the simulator's expected outcomes.

## 5. Functional requirements

| ID | Requirement |
|---|---|
| FR-1 | Accept clearance events on a Kafka topic, keyed by `shipment_id`. |
| FR-2 | Reject events that fail the envelope or payload schema to the DLQ with `SCHEMA_INVALID`. |
| FR-3 | Reject events whose container ID fails ISO 6346 format or check-digit validation with `CONTAINER_ID_INVALID`. |
| FR-4 | Reject events whose UN/LOCODE port or HS code is not in the reference data with `UNKNOWN_REFERENCE_DATA`. |
| FR-5 | Store each valid event only once (deduplicated by `event_id`) in an append-only event log. |
| FR-6 | Derive each shipment's current state by folding its events in event-time order, so that late and out-of-order events self-heal. |
| FR-7 | Record each illegal transition as an `ILLEGAL_TRANSITION` anomaly without changing state, and re-derive anomalies on every recompute. |
| FR-8 | Count dropped duplicates. |
| FR-9 | Raise exactly one alert per hold (per `shipment_id` + `state_since`) once a shipment has been `ON_HOLD` longer than `HOLD_ALERT_SECONDS`. |
| FR-10 | Persist DLQ messages as rejections that can be queried by reason code, without double-counting on replay. A message that keeps failing for an unexpected reason is quarantined as `PROCESSING_ERROR` rather than crash-looping the service. |
| FR-11 | API: get one shipment's current status. |
| FR-12 | API: get one shipment's event history in fold order. |
| FR-13 | API: list shipments by state, paginated, with a maximum page size. |
| FR-14 | API: list anomalies and alerts, return rejection counts by reason, and return pipeline stats. |
| FR-15 | Simulator: a seeded, reproducible event stream with configurable fault rates, plus the expected outcomes for that seed. |
| FR-16 | One command runs the full pipeline and prints a summary checked against the simulator's expected outcomes. |
| FR-17 | Run in Docker Compose and on Kubernetes (kind), with the processor able to scale horizontally. |
| FR-18 | CI runs lint, unit tests and a Compose smoke test on every push. |

## 6. Success metrics (all measured by the demo; no invented numbers)

- **M1 (correctness):** In a clean demo run, the final state counts, anomaly count, DLQ counts by reason and duplicate count all equal the simulator's expected values.
- **M2 (no silent loss):** `produced = stored + duplicates_dropped + rejected` holds exactly in a clean run.
- **M3 (idempotency):** Replaying the same stream a second time changes no shipment state, and the event count stays the same.
- **M4 (order independence):** Any permutation of arrival order gives identical final states (a unit test plus a shuffled replay).
- **M5 (recovery):** After the processor is killed mid-run and restarted, all of M1 still holds.
- **M6 (alerts):** Each shipment left on hold produces exactly one alert, including across monitor restarts.
- **M7 (operability):** The pipeline starts from a clean clone using only the README, and CI is green.

## 7. Assumptions

- Each source stamps `occurred_at` correctly in UTC (clock skew is out of scope).
- `event_id` is unique per logical event. A source that re-sends with a new `event_id` will not be detected as a duplicate.
- One container per shipment.
- Demo scale is hundreds of shipments, not millions.

## 8. Risks

Measured on 2026-10-11 (DECISIONS.md, Environment record): 7.8 GB RAM, C: 99% full, Docker engine stopped, kind and Python 3.11 not installed.

| Risk | Mitigation |
|---|---|
| RAM: 7.8 GB total with 0.8 GB free | Native Kafka image, a 0.25 GB MongoDB cache, Kafka UI only on demand, a memory limit on every container, and Compose and kind never running together (D-039). Usage is measured in P3 and P11. If kind does not fit, Release 1 stands and bullet 2 is cut. |
| Disk: C: has 3.7 GB free | Everything is on D: (D-040). The Docker disk image must be moved to D: before P3 (user action). |
| Python 3.11 not installed | uv-managed 3.11 installed into D:, with no system change (D-041) |
| A CI failure only shows up after the user pushes | CI runs exactly the local acceptance commands (D-042) |
| Kafka listener misconfiguration (host vs. in-network) | Two listeners, documented in ARCHITECTURE.md §5, and tested in Phase 3 |
| Timing-dependent demo results (alerts) | Defaults with at least 15 s of margin, enforced by the simulator CLI (TRD §11) |
| The demo's expected values reuse the fold logic | The fold is proven separately by exhaustive unit tests in Phase 2, so the demo tests the plumbing around it |
| A resume claim not backed by the build | Bullets reworded to match the design, and each one mapped to evidence (IMPLEMENTATION_PLAN.md, D-038) |

## 9. Data disclosure

All events are **synthetic data**. The bundled reference CSVs are small hand-picked subsets (about 30
ports and about 20 HS codes) used only for format and lookup validation.
